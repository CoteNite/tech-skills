# 深挖契约

第 5 步读这份文件：每个候选派一个 subagent，返回一张**候选卡**，原始材料写进证据目录。

## 取证档位

档位决定置信度，不能跳级汇报。

| 档位 | 做什么 | 证据 |
|---|---|---|
| `读` | 仓库元数据、README、官方文档、依赖清单、许可证、发布与提交活跃度 | `meta.json`、`tree.txt`、`deps.txt`、`license.txt` |
| `挖` | `git clone --depth 1` 后读关键源码：入口、核心模块、配置与扩展点 | 上述 + `文件:行` 摘录 |
| `跑` | 按官方路径本地实跑最小验证（构建、起服务、跑 demo），或对需求核心链路做最小 PoC | 上述 + `run.log`（命令原文与输出） |

`挖` 是默认下限：只读 README 得出的"可行"结论，在甲方那里一撞就碎。
`跑` 只在需求核心链路存在真实不确定性时开（例如"能不能离线部署""能不能换国产数据库"），且由确认门点头。

## 档位是上限

brief 里给的档位是**上限**，不是建议：

- 档位 ≤ `挖`：只读源码，不构建、不启动、不压测。命令只用 `git clone --depth 1`、`grep`、`read`。
- 档位 = `跑`：只跑官方文档给的**最小**路径（构建、起服务、跑自带 demo），不做压测、不改仓库配置去凑结论。

某条 Ci 靠当前档位答不出来时，**不得自行升级**：回报「建议升级到 `跑` —— 跑什么、能证伪哪条假设、大概多久」，由主线转交用户裁决。**主线无权放行**：确认门批准的是候选范围与档位分配，确认门之外新增的实跑一律要用户点头。条子批不下来的，把该条写进「未实证假设」，并在卡尾「建议越档」节留记录。

越档获批并跑过之后，在档位栏写实际达到的等级（`跑` → 置信度 `高`）——档位与置信度必须与实际证据一致。

已归档、或两年以上无提交的仓库，默认档位降为 `读`：这类项目通常只会进"仅供参考"或"硬筛除"，先按元数据判，值不值一次克隆由确认门定。真去挖了，就在卡里说明为什么值得。

## 命令清单

`<skill-dir>` 是本 skill 目录的真实绝对路径（由加载本 skill 的机制给出，派 subagent 时先替换成实际路径）。

```bash
# 元数据：GitHub 与 Gitee 同一入口，产出 meta.json / tree.txt / deps.txt / license.txt / activity.txt / PROBE.md
python <skill-dir>/scripts/repo_probe.py <证据目录> github:owner/name gitee:owner/name
python <skill-dir>/scripts/repo_probe.py <证据目录> github:owner/name --clone   # 顺带浅克隆

# 挖：浅克隆
git clone --depth 1 https://github.com/owner/name.git <临时目录>/src
git -C <临时目录>/src rev-parse HEAD   # 先记 SHA，克隆删了也能按 SHA 重取

# 读源码：优先按能力清单找入口，别漫游
grep -rn --include='*.java' -e 'class .*Service' <src>/src/main/java | head -30
# 跑：官方文档给的构建/启动路径，原样执行，输出整段贴进 run.log
```

Windows 上不要用 `bash <脚本>` 的写法：PATH 里的 `bash` 往往是 WSL 的 `/bin/bash`，跨 Windows/MSYS 路径会直接失败。直接调 `python` 即可。

## 候选卡契约

固定结构，主线按这份契约合流。缺字段就是没做完，不要用"待补充"糊过去。

```markdown
### <候选名>（<平台> <owner/name>）

- 仓库：<URL> ｜ 主语言：<lang> ｜ Stars：<n> ｜ 最近提交：<date> ｜ 许可证：<SPDX 或 LICENSE 首行>
- 提交 SHA：<sha>（克隆删了也能重取）
- 档位：读 / 挖 / 跑 ｜ 置信度：低 / 中 / 高
- 结论词：可直接复现 / 需改造可复现 / 仅供参考不可直接复现 / 不建议

#### 技术实现逻辑

- 架构与关键模块：<模块 → 职责，逐条>
- 关键路径（`文件:行`）：<引用 → 说明它做了什么>
- 核心依赖与协议：<依赖 → 作用；用到的协议/标准>
- 可移植借鉴点：<值得照搬的路径与理由> ／ <不可照搬的路径与理由：许可证、架构强绑、体量>

#### 能力映射

| 能力 | 结论 | 依据 |
|---|---|---|
| C1 | 已实现 / 部分实现 / 缺失 / 需改造 | `文件:行` 或文档链接 |

#### 可复现性

- 构建与运行依赖：<工具链、版本要求、平台限制>
- 外部服务依赖：<数据库、中间件、云服务、账号>
- 文档完备度：<官方快速开始能否照做；缺哪一块>
- 许可证与合规：<以 LICENSE 文件原文为准；对交付形态的影响>

#### 可行性

- 与既有技术栈契合度：
- 集成点与二次开发扩展点：<改哪里、改多少处>
- 工作量量级：<量级 + 依据；不报精确工期>
- 风险：<每条带触发条件与影响>

#### 面向交付的取舍（供汇报稿取用）

这几栏是汇报稿 1.2 / 1.3 / 第三章的素材，**必须写具体**；写不出就明说"未取得数据"，不要留空。

- **运维代价**：<部署形态（单机/容器/多实例、Windows 还是 Linux）、资源占用（CPU/内存/磁盘，有实测就写实测值）、外部依赖（数据库/中间件/云服务、能否离线）、日常运维要做的事与所需人员水平、升级与回滚方式。逐项一句。>
- **出厂默认态**：<开箱即用的默认配置是有防护还是"装了但没在防"；哪些能力默认关闭、哪些默认上报外网、是否有默认凭据。这一栏决定交付前要补什么。>
- **可借的具体做法**：<值得照搬的机制，逐条写"机制 + 为什么值得借"，不写文件位置。这条是汇报稿"值得借鉴的地方"的唯一来源。>
- **相对同类的差异点**：<相比同批候选，它在哪个维度上强、哪个维度上弱，依据是什么。写不出对比就写"与同批候选无显著差异"。>

#### 未实证假设

- <假设 → 影响哪个结论 → 怎么才能证伪>

#### 建议越档

<档位没到位时的证据缺口。只写"跑什么、能证伪哪条假设、大概多久"，不写实施细节；档位已到 `跑` 或没有缺口就写「无」。>
```

## 给 subagent 的 brief 模板

```text
# 目标
对候选仓库 <owner/name>（<平台>，URL）做技术实现调研，取证档位 = <读|挖|跑>。

# 背景：甲方需求与能力清单
<粘贴需求原文摘录与 C1..Cn；这份清单来自主线，不要自行改写>

# 已知
- 输出目录（证据）：<绝对路径>/evidence/<候选slug>/
- 报告语言：中文

# 步骤
1. 运行 `python <skill-dir>/scripts/repo_probe.py <证据目录> <平台>:<owner/name>`（`--clone` 可顺带浅克隆），拿到元数据。
   许可证以克隆后的 LICENSE 文件原文为准，不要信搜索接口的 license 字段。
2. 档位 ≥ 挖 时：`git clone --depth 1` 到临时目录，记下 `git rev-parse HEAD`，然后按能力清单
   逐条找实现位置。只读与 C1..Cn 相关的关键路径，不做全仓漫游。
3. 档位 = 跑 时：按官方文档的最小路径实跑，命令与输出原样落进 run.log；跑不通也要记录失败点。
4. 原始材料（meta.json、tree.txt、deps.txt、license.txt、activity.txt、run.log、源码摘录）留在证据目录，
   克隆在记录 SHA 后可删。
5. 回一张候选卡，严格用 brief 里贴的契约结构，不留"待补充"。「面向交付的取舍」那节必须写具体。

# 约束
- 档位由主线指定，**你不得自行升级**：≤ 挖 时不构建、不启动、不压测；= 跑 时只跑官方文档的最小路径。确实需要实跑时，回报「建议升级到 跑：跑什么、能证伪哪条假设、多久」，由主线转交用户裁决。
- 每个技术判断都要能给出来源：`文件:行`、官方文档或命令输出。给不出就写进「未实证假设」。
- 只读文档/元数据得出的判断，档位就是 `读`，置信度就是 `低`，不要升格。
- 不安装重型依赖、不改被调研仓库的配置或代码；被调研仓库保持 `git status --porcelain` 干净。
- 不写报告正文，只回候选卡 —— 报告由主线合流写出。契约结构以 brief 里贴的那份为准。

# 验收
候选卡里 C1..Cn 每条都有结论与依据；实现逻辑节至少有 3 条 `文件:行` 引用（档位 = 读 时可为零，但要说明）。
「面向交付的取舍」四栏都写具体，写不出的明说"未取得数据"。
档位栏写实际达到的等级；越档跑过要标出来。
```

## 合流

候选卡是**两份**文档的共同输入：主线把它们按相同结构拼进 `report.md` 的第 3 节，再据同一批证据写 `调研汇报.md`（不重跑调研）。

为了让汇报稿有素材，卡片里多了一节「面向交付的取舍」——汇报稿的运维代价、可借做法、相对差异全部从这里取，**不要到汇报阶段现编**。

然后：

- 矩阵与速览里的结论，直接取自各卡的结论词，不重新判定。
- 把各卡「未实证假设」节汇总进报告的「未实证假设与置信度」节，并补上跨候选的共性假设；能靠实跑消掉的排最前。
- 各卡「建议越档」里被用户点头的条目，写成下一轮动作；没点头的留在假设表里。
- 若某条 Ci 在多个候选上都「缺失」，写进推荐的兜底段：这部分自研或采购。
- 置信度取该候选卡的档位，不许因为"读了两篇博客"而上调。

**写汇报稿时**（第 7 步）：事实全部取自 `report.md`，允许重复；删到实现级为止，机制与数值保留；不新增 `report.md` 里没有依据的判断。卡里的 `文件:行` 引用是给 `report.md` 用的，进汇报稿前必须转写成机制描述（「检测器统一签名、按顺序注册」而不是「`wafengine.go:578` 的检测器数组」）。

## 证据目录命名

`<候选slug>` 用 `repo_probe.py` 生成的名字：`<平台>-<owner>_<name>`，例如 `github-fhmq_hmq`。
主线与 subagent 用的是同一个 slug，别各起一套。

## 转存镜像仓

拿到 `gitee.com/mirrors/*`、`Gitee 极速下载/*` 这类 URL 时，先找它指向的上游原始仓库，改用上游做取证：镜像仓是滞后快照，且元数据大面积失真（描述、语言、Stars 都可能挂到别的项目上）。上游也在 Gitee 的项目（如 `ThingsPanel/*`）直接用 Gitee 自有仓即可。
